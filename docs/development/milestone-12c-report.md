## Scope and implementation

The two approved ADR 0006/M12 specification provenance amendments were copied byte-for-byte from the preserved M12B worktree. Marker-v2 parsing now enforces the 1,024-byte bound, strict UTF-8, exact fields, duplicate-key rejection, UUID/handle/profile rules and location fingerprinting. A binding verifier compares the immutable database singleton with configuration, both parsed role markers and provider-observed physical evidence. It returns only sanitized 503 errors. The new Linux observer is registered with the verifier in `StorageModule`; the active M11 media service and M12 startup refusal remain unchanged. Unit and disposable PostgreSQL tests exercise the verifier with synthetic observations; these tests do not certify a physical filesystem.

A typed provider contract and local implementation now provide bounded exclusive staging, file sync, hard-link no-replace publication, directory sync, logical target validation, regular-file reads, exact removal and authoritative absence on a verified binding. A process-local receipt retains the attempt's staging hard link as physical proof for compensation; a collision never overwrites, and ambiguous publication retains possible files. The provider pins the role directory, verifies the marker and physical identity on that descriptor, and performs file operations through `/proc/self/fd` while it remains open. A synthetic parent-substitution test confirms that publication cannot be redirected into a replacement directory. Both role bindings are rechecked around operations; no missing roots are created. The provider and image adapter are registered for dependency injection but do not replace the active M11 asset-storage token. Focused native ext4 checks passed; crash and power-loss durability remain **uncertified**.

An unmounted image adapter uses that provider to preserve original bytes, validate multipart completion and image metadata, generate a bounded JPEG thumbnail, retain uncertain outcomes and compensate only receipts from its own attempt. `AssetsService` can release staging links after an acknowledged database commit; the active M11 storage implementation remains the production binding until a certified observer and reviewed M12 startup replacement exist. The shared asset-ID advisory lock is now taken in upload finalization after the user and session row locks, and the deletion journal is checked before insertion on M12 schemas. Historical M11-schema fixtures have no journal and retain their original upload behavior; M12 readiness continues to reject incompatible schema.

An explicit fresh-install primitive requires empty asset, deletion and binding tables plus empty pre-existing role directories, observes both identities, writes exclusive persistent markers, re-observes them, then inserts the singleton under a short table-locked transaction. Unknown COMMIT acknowledgement is resolved only by an independent exact-tuple read. Partial marker writes are retained for operator recovery. A separate interactive `storage:provision-fresh` command now requires distinct operator database environment variables and exact database/root confirmations; it never runs from API startup and was **not** executed against real data. A read-only historical-adoption preflight now compares a reviewed manifest with every database asset row and the complete synthetic originals/thumbnail inventory, including sizes and SHA-256 digests; it rejects unexpected files and does not insert a binding or write markers. This is a necessary check, not proof of human-reviewed provenance or authorization to adopt. The actual adoption transaction, relocation and restoration remain unimplemented. No permanent-deletion route, executor or background job was added.

The operator notes describe the approved evidence and recovery procedure. A focused isolated HTTP fixture composes the provider-backed media adapter with synthetic binding evidence: original and thumbnail bytes stream when verified, while loss of the database anchor returns sanitized JSON 503 for both. This is not real-process M12 activation or native ext4 evidence. Architecture and backend guidance identify the merged M12B schema and continuing startup gate.

The Linux-only C helper accepts only inherited role-directory fd 3. It checks `fstat`/`fstatfs` for a directory on ext4, calls `FS_IOC_GETFSUUID` and unprivileged `name_to_handle_at(..., AT_EMPTY_PATH)` on that same descriptor, reads the bounded marker with `openat(O_NOFOLLOW)`, reobserves identity, and emits bounded JSON. The TypeScript adapter checks path components, pins the directory descriptor, invokes the helper with a three-second timeout and 4 KiB output cap, validates the exact protocol, and rejects inconsistent evidence or a replaced path. Linux builds compile the helper to `server-nest/dist/native/storage-identity-observer` with `cc`, libc and installed Linux UAPI headers. No new npm dependency or elevated runtime capability is required. This local host did **not** provide a safe ext4 test environment; the separate GitHub-hosted VM supplied the successful native observations below.

A focused GitHub Actions workflow uses a GitHub-hosted `ubuntu-24.04` VM, read-only repository token and fresh regular image files under the runner's temporary directory. Only the disposable VM formats and mounts those image files. The native script records runner/kernel/filesystem details, checks independent ext4 identities, copied markers, unsupported/missing mounts and a capability-free non-root container. It has a local guard that refuses execution outside the expected hosted VM. The draft-PR trigger is needed because [GitHub requires a manual-dispatch workflow to exist on the default branch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow); manual dispatch can be used after the workflow reaches that branch. No hosted result is claimed until the run completes.

## Focused security and data-safety review

The current application still rejects all M12-schema HTTP startup. The verifier, local provider and image adapter are registered in `StorageModule`, but the active M11 storage token is unchanged and M12 media cannot start. Binding failures become sanitized unavailable outcomes. Marker parsing bounds input and rejects ambiguous or incomplete evidence. Existing authentication, owner queries, active M11 storage, historical migrations and accepted ADRs are unchanged. The upload transaction now acquires user row, session row and asset-ID lock in order, then checks retained journal IDs. Future deletion acceptance must use the same asset-ID lock. No database connection is held while image bytes are written.

The helper uses the [Linux handle syscall contract](https://man7.org/linux/man-pages/man2/name_to_handle_at.2.html) and [Linux UUID ioctl definition](https://github.com/torvalds/linux/blob/master/include/uapi/linux/fs.h). It never calls privileged `open_by_handle_at`, accepts an application pathname, opens a block device or falls back to `st_dev`/inode/path identity. Its stdout carries physical evidence only on the parent pipe; stderr is generic and suppressed by the adapter. Unsupported ext4/kernel/container behavior, including failure of the UUID ioctl or file-handle syscall, remains unavailable. Focused native ext4 checks passed on one hosted runner profile; crash and power-loss persistence guarantees are **unverified**, so the observer is not an M12 HTTP activation claim.

## Remaining security and compatibility gates

This local host's `/tmp` is tmpfs and its development paths are btrfs. The only observed local ext4 mount is `/boot`, which was not used. QEMU is installed, but no usable `/dev/kvm` or prepared disposable guest image was available; no local host loop device, formatting, mount or privileged alternative was attempted. The isolated GitHub-hosted VM supplied native ext4 and non-root container evidence. The focused post-link process kill passed, but full database/FS crash recovery, VM failure and power-loss evidence remain unavailable; a normal unmount/remount is insufficient. Unsupported observation stays unavailable without pathname, inode or device-number fallback. Existing provider tests inject staged-file and directory-sync failures, and the synthetic HTTP test checks unavailable media.

Further certification should cover reboot/container recreation, denied syscalls, fsync failure, partial removal and abrupt VM termination under documented cache assumptions. The hosted run already covered distinct disposable ext4 images, copied markers, non-root container execution, exact-byte publication/read/removal, a normal remount, and missing/swapped mounts. No filesystem was mounted or formatted on this local host, and `/boot` was not used. VM crash tests still cannot prove every hardware power-loss mode.

A fresh-only operator command is implemented but not approved for real use. Historical-adoption inventory assessment exists, but there is no executable adoption, relocation or restoration cutover. Provider replacement of the active M11 token and real-process M12 startup activation remain incomplete. The Node provider pins the target role directory and operates through `/proc/self/fd` instead of re-resolving configurable parent paths; synthetic tests and the focused hosted checks do not prove all mount-namespace and crash behavior. The provider's exact-removal method is **not exposed** as a destructive HTTP API. A process crash can leave staging hard links or published media; uncertain PostgreSQL commits retain possible files for explicit reconciliation. M12B's blanket M12 HTTP startup refusal stays intact. No M12C media behavior is ready for deployment or real-data upgrade.
