## Scope and implementation

The two approved ADR 0006/M12 specification provenance amendments were copied byte-for-byte from the preserved M12B worktree. Marker-v2 parsing now enforces the 1,024-byte bound, strict UTF-8, exact fields, duplicate-key rejection, UUID/handle/profile rules and location fingerprinting. A binding verifier compares the immutable database singleton with configuration, both parsed role markers and provider-observed physical evidence. It returns only sanitized 503 errors. The Linux observer is registered with the verifier in `StorageModule`. Unit and disposable PostgreSQL tests exercise the verifier with synthetic observations; these tests do not certify a physical filesystem.

A typed provider contract and local implementation now provide bounded exclusive staging, file sync, hard-link no-replace publication, directory sync, logical target validation, regular-file reads, exact removal and authoritative absence on a verified binding. A process-local receipt retains the attempt's staging hard link as physical proof for compensation; a collision never overwrites, and ambiguous publication retains possible files. The provider pins the role directory, verifies the marker and physical identity on that descriptor, and performs file operations through `/proc/self/fd` while it remains open. A synthetic parent-substitution test confirms that publication cannot be redirected into a replacement directory. Both role bindings are rechecked around operations; no missing roots are created. The schema-aware storage token now selects this adapter only for an exactly validated M12 schema and retains the legacy adapter for an exactly validated M11 schema; invalid history never falls back. Focused native ext4 checks passed; crash and power-loss durability remain **uncertified**.

The image adapter preserves original bytes, validates multipart completion and image metadata, generates a bounded JPEG thumbnail, retains uncertain outcomes and compensates only receipts from its own attempt. `AssetsService` can release staging links after an acknowledged database commit; upload readiness now checks the binding before multipart parsing. The shared asset-ID advisory lock is taken in upload finalization after the user and session row locks, and the deletion journal is checked before insertion on M12 schemas. Historical M11-schema fixtures have no journal and retain their original upload behavior. Production startup now accepts exact M11 history unchanged and exact M12 history after the M12 readiness assessment; storage unavailability yields authenticated metadata-only operation. Invalid or partial schema refuses startup before listening. Bound media remains gated by both role identities at every operation, with no legacy fallback.

The independent M12C review found two blocking regressions. Upload finalization now rechecks session expiry using PostgreSQL `clock_timestamp()` after any asset-ID lock wait and before insertion. A disposable-database test holds that advisory lock on an independent connection until an initially valid session expires, then proves the insert rolls back with 401; a normal insertion still succeeds. This preserves user → session → asset-ID lock order and does not hold a SQL transaction during filesystem publication. The test verifies the metadata boundary; existing upload compensation tests cover retention of unrelated media and uncertain publication separately.

Bound upload classification now distinguishes empty input, source/caller failure, size excess and storage failure. Multipart completion verification executes outside Sharp's image-decoding catch, so recognized parser errors remain 400, size excess remains 413, empty/invalid images remain 415, and unavailable storage remains sanitized 503. The controller rejects a file stream already destroyed by a malformed multipart request instead of awaiting a pipeline event that has already occurred. Focused bound-provider HTTP tests cover these statuses, an extra-field completion failure, a truncated real-socket request, a mid-stream socket disconnect with staging cleanup, and a successful byte-exact upload. A client that has disconnected cannot receive an HTTP response; the disconnect test asserts cleanup and no metadata insertion instead.

An explicit fresh-install primitive requires empty asset, deletion and binding tables plus empty pre-existing role directories, observes both identities, writes exclusive persistent markers, re-observes them, then inserts the singleton under a short table-locked transaction. Unknown COMMIT acknowledgement is resolved only by an independent exact-tuple read. Partial marker writes are retained for operator recovery. The interactive fresh and historical-adoption commands require distinct operator database credentials and exact confirmations; they never run from API startup and were **not** executed against real data. Historical adoption consumes a protected operator evidence file outside the media root, checks every database asset row and complete original/thumbnail inventory with sizes and SHA-256 digests, verifies two native role identities, writes markers exclusively, and inserts the singleton under a short table lock with exact-tuple unknown-COMMIT confirmation. The confirmation flags do not mechanically prove writer fencing or backup validity.

Controlled relocation/restoration has a separate explicit command and read-only full-pairing inventory gate. It compares the unchanged database binding, complete ordered asset and deletion-journal row digests, and every file's size/hash at the destination, including staging residue. It rejects copied markers, incomplete or extra files and changed SQL, then exclusively establishes fresh physical marker evidence with the existing logical IDs. It never changes asset metadata, journal targets or the binding row. Partial marker writes remain unavailable for operator investigation. Synthetic disposable PostgreSQL tests cover accepted cutover, incorrect backup hash, copied marker rejection, repeat refusal and unchanged historical rows. This does **not** prove an actual backup exists, fence external processes, certify a native relocation, or authorize real-data use. No permanent-deletion route, executor or background job was added.

Independent-role relocation remains unavailable. The current recovery inventory requires a complete two-role pairing and rejects an existing marker in either role. Safely preserving an unchanged role's marker while re-establishing evidence for the moved role needs a separately reviewed evidence and cutover protocol; this correction does not guess at one. A moved originals or thumbnails root alone must continue to fail closed.

The operator notes describe evidence and recovery prerequisites. A focused isolated HTTP fixture composes the provider-backed media adapter with synthetic binding evidence: original and thumbnail bytes stream when verified, while loss of the database anchor returns sanitized JSON 503 for both. An earlier guarded hosted-ext4 run composed `AppModule` on a loopback socket with disposable PostgreSQL and passed three tests; that run preceded the production cutover. The current hosted test has been changed to launch compiled `dist/main.js` children for unadopted and adopted startup, wrong pairing, and post-startup marker, role or helper loss. Its result remains pending until the new milestone-branch workflow runs.

The Linux-only C helper accepts only inherited role-directory fd 3. It checks `fstat`/`fstatfs` for a directory on ext4, calls `FS_IOC_GETFSUUID` and unprivileged `name_to_handle_at(..., AT_EMPTY_PATH)` on that same descriptor, reads the bounded marker with `openat(O_NOFOLLOW)`, reobserves identity, and emits bounded JSON. The TypeScript adapter checks path components, pins the directory descriptor, invokes the helper with a three-second timeout and 4 KiB output cap, validates the exact protocol, and rejects inconsistent evidence or a replaced path. Linux builds compile the helper to `server-nest/dist/native/storage-identity-observer` with `cc`, libc and installed Linux UAPI headers. No new npm dependency or elevated runtime capability is required. This local host did **not** provide a safe ext4 test environment; the separate GitHub-hosted VM supplied the successful native observations below.

A focused GitHub Actions workflow uses a GitHub-hosted `ubuntu-24.04` VM, read-only repository token and fresh regular image files under the runner's temporary directory. Only the disposable VM formats and mounts those image files. The native script records runner/kernel/filesystem details, checks independent ext4 identities, copied markers, unsupported/missing mounts and a capability-free non-root container. It has a local guard that refuses execution outside the expected hosted VM. The milestone branch now has a path-limited `push` trigger and an exact-branch job condition; arbitrary pull requests cannot start native filesystem preparation. Manual dispatch remains available once [GitHub's default-branch workflow requirement](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) is satisfied. No new hosted result is claimed until the run completes.

## Focused security and data-safety review

The production bootstrap now calls the exact-history authentication readiness check and invokes the M12 binding-aware assessment before listening on M12 schemas. The schema-aware image token selects the bound provider only after exact M12 history validation and rechecks binding at every media operation; M11 history selects the legacy implementation. Binding failures become sanitized unavailable outcomes. Marker parsing bounds input and rejects ambiguous or incomplete evidence. Existing authentication, owner queries, historical migrations and accepted ADRs are unchanged. The upload transaction acquires user row, session row and asset-ID lock in order, then checks retained journal IDs. Future deletion acceptance must use the same asset-ID lock. No database connection is held while image bytes are written.

The helper uses the [Linux handle syscall contract](https://man7.org/linux/man-pages/man2/name_to_handle_at.2.html) and [Linux UUID ioctl definition](https://github.com/torvalds/linux/blob/master/include/uapi/linux/fs.h). It never calls privileged `open_by_handle_at`, accepts an application pathname, opens a block device or falls back to `st_dev`/inode/path identity. Its stdout carries physical evidence only on the parent pipe; stderr is generic and suppressed by the adapter. Unsupported ext4/kernel/container behavior, including failure of the UUID ioctl or file-handle syscall, remains unavailable. Focused native ext4 checks passed on one hosted runner profile; crash and power-loss persistence guarantees are **unverified**, so the observer is not an M12 HTTP activation claim.

## Remaining security and compatibility gates

This local host's `/tmp` is tmpfs and its development paths are btrfs. The only observed local ext4 mount is `/boot`, which was not used. QEMU is installed, but no usable `/dev/kvm` or prepared disposable guest image was available; no local host loop device, formatting, mount or privileged alternative was attempted. The isolated GitHub-hosted VM supplied native ext4 and non-root container evidence. The focused post-link process kill passed, but full database/FS crash recovery, VM failure and power-loss evidence remain unavailable; a normal unmount/remount is insufficient. Unsupported observation stays unavailable without pathname, inode or device-number fallback. Existing provider tests inject staged-file and directory-sync failures, and the synthetic HTTP test checks unavailable media.

Further certification should cover reboot/container recreation, denied syscalls, fsync failure, partial removal and abrupt VM termination under documented cache assumptions. The hosted run already covered distinct disposable ext4 images, copied markers, non-root container execution, exact-byte publication/read/removal, a normal remount, and missing/swapped mounts. No filesystem was mounted or formatted on this local host, and `/boot` was not used. VM crash tests still cannot prove every hardware power-loss mode.

Operator commands for fresh provisioning, historical adoption and controlled location re-establishment are implemented but not approved for real use. Their confirmations cannot establish actual writer fencing or backup integrity; operators must separately verify those prerequisites. Native relocation/restoration and full database/FS crash recovery remain unverified. The Node provider pins the target role directory and operates through `/proc/self/fd` instead of re-resolving configurable parent paths; synthetic tests and focused hosted checks do not prove all mount-namespace and crash behavior. The provider's exact-removal method is **not exposed** as a destructive HTTP API. A process crash can leave staging hard links or published media; uncertain PostgreSQL commits retain possible files for explicit reconciliation. M12 HTTP startup is enabled on this feature branch for exact validated schema, while all unverified media stays unavailable. No M12C media behavior is ready for deployment or real-data upgrade.

The compiled `main.ts` child-process tests passed locally for valid historical M11 startup/SIGTERM shutdown, exact M12 metadata-only startup with empty or synthetically populated binding, and empty/partial-schema refusal before listening. They confirm owner metadata remains available while original reads and uploads return sanitized 503 without verified storage. The guarded hosted ext4 suite will test compiled-process adopted upload/original/thumbnail behavior, wrong pairing, marker/role/helper loss, session and Origin/CSRF controls.
