## Implementation

`server/src/worker/` contains an independently booted Nest application context, separate worker configuration, a versioned synthetic-only job contract, a BullMQ runtime, an independent periodic scheduler-repair loop, process-local diagnostics, and a pure synthetic recovery-gate validator. It imports no API, asset, database, storage or M12 deletion module. `npm run start:worker` starts no HTTP listener. There is no real deletion handler, automatic Trash expiry, database query, real permit file or storage access.

`bullmq` is pinned at `5.81.5` in `server/package.json` and `server/package-lock.json`; it supplies its own Redis client dependency. Node.js 24 and the current BullMQ Job Scheduler API were used. The only scheduled job is `synthetic.ping.v1`; payload validation accepts exactly `{version: 1, nonce: UUID}`. The processor returns a synthetic acknowledgment, never a deletion outcome.

The worker defaults to loopback Redis (`127.0.0.1:6379`), one concurrent synthetic job, a 60-second control tick and a 60-second synthetic schedule. Remote Redis requires TLS and a password. Concurrency is bounded to 1–4; queue retention is bounded to 100 completed and 100 failed jobs. The Queue uses short request retry limits and producer-only command/socket timeouts; the Worker retains BullMQ's required unlimited per-request retries for blocking consumption. Startup waits for Redis and the first scheduler check; unavailable Redis fails startup. A live independent timer repairs a missing synthetic scheduler and records degraded state on failure. Repeated sanitized error logs are rate-limited.

**Corrective pass:** The prior `close(false)` then `close(true)` sequence could never escalate because BullMQ 5.81.5 returns the original closing promise. Shutdown now stops intake with `pause(true)`, waits at most five seconds for tracked synthetic processors, then calls `close(true)` as its **first** BullMQ close. Producer commands and the queue are closed within separate bounded windows. A timed-out processor or unconfirmed resource closure yields an observable `incomplete` state; the real worker process exits nonzero if shutdown is incomplete or exceeds its overall 15-second watchdog. This process exit does not cancel an already-issued filesystem call, and the M13B deletion executor must use its own journal and fencing rules. Signal handling cancels in-progress startup before it can install a timer or report ready.

**Final shutdown correction:** BullMQ's forced-close promise does not prove that the consumer run loop, its outstanding Redis calls or a late stalled-check timer have settled. The runtime now awaits its tracked `worker.run()` task with a separate bound after the first forced close and refuses a clean result if that task is unsettled, rejected, still running, or a synthetic processor remains active. During a silent Redis outage, producer commands can close while the consumer remains uncertain; shutdown correctly reports `incomplete`. The real process keeps its 15-second watchdog through runtime and Nest context shutdown, then unreferences it rather than clearing it. A clean process exits naturally with code 0; any late handle keeping it alive reaches the deadline and exits 1. Repeated signals reuse the same shutdown task and deadline. The watchdog is a process boundary, not proof that BullMQ or a future filesystem call was canceled.

Previously, a `Promise.race()` timeout returned from a control tick while the Redis command remained queued, letting later ticks accumulate commands. The corrected producer uses a four-second command timeout and five-second socket timeout, tracks unsettled producer promises and limits concurrent synthetic enqueues. A failed producer is disconnected before replacement; the old ioredis socket reaches `end` and its command queue is flushed. The independent timer verifies the scheduler on the new connection. The blocking consumer retains its separate connection policy. Readiness now requires a successful producer check, live consumer run loop and ready consumer connections; a scheduler query alone cannot restore a failed consumer. A timeout still makes a synthetic enqueue outcome uncertain, so callers receive a bounded failure rather than an invented delivery acknowledgment.

The Redis test runner now requires an explicit `PONG` within its bounded readiness probes. The tests observe the actual named duplicate job and its execution count, the periodic scheduler repair, delayed stale payload rejection, completed-job retention, active work beyond shutdown grace and process signaling before startup readiness.

**Leadership boundary:** M13A expects one worker process. Its control loop is process-local and only repairs synthetic schedules; duplicate control ticks would not grant deletion authority. Before M13B real reconciliation, approve and implement a short PostgreSQL lease with database-clock expiry, fencing generation and persisted finite-pass checkpoint. No distributed lease or authoritative reconciliation is claimed here.

**Recovery boundary:** `syntheticGateAllows` is a pure fail-closed test stub. It does not read, create, arm or validate a real external recovery permit. The independently controlled real execution gate and controlled-restore procedure remain mandatory M13B prerequisites.

## Isolation, risks and next gate

The Redis test runner uses a random labeled `redis:7.4` container, random credential, tmpfs-only data, a random `127.0.0.1` port, identity checks before tests and cleanup, signal forwarding and verified removal. It does not use Compose, a named volume or the application's `.env`. The existing PostgreSQL runner similarly verified and removed its isolated PostgreSQL 18 container. Neither runner accessed the development database, media roots or persistent Docker volumes.

The Redis deployment profile is **not** configured or certified by M13A. A future operational configuration needs secured networking, persistence/noeviction, backups and recovery; PostgreSQL remains the deletion authority. The suite tests Redis pause and local producer replacement, not a container restart or loss of Redis data. The new child-process regression exercises an equivalent late event-loop handle after shutdown work settles; it does **not** reproduce BullMQ's exact stalled-check Redis-command ordering. The run-loop settlement check and process-exit deadline address that source-identified risk, but direct fault injection of BullMQ's internal maintenance query remains untested. The in-process diagnostics have no operator HTTP endpoint yet. Multi-worker leadership, real restoration fencing, durable receipt scans, retry generations and resource accounting shared with the API remain M13B decisions and tests. A prior `npm install` audit reported six unresolved advisories (two low, four moderate); the prior production-only audit reported three entries (two low, one moderate): `@nestjs/platform-fastify` through Fastify, Fastify 5.12.5, and `fast-uri` 3.1.8/4.2.2 through the Fastify JSON-schema stack. No M13A exploit was demonstrated; remediation remains a separate dependency task before public alpha. Audit was not rerun in the corrective pass. Current architecture/roadmap documents contain older M12 feature-branch status wording; they were left unchanged outside this phase.
