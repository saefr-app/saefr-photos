## 2. Approved ownership schema

Append `202610220001_asset_ownership.ts`; recheck identifier/name collisions before 11B. No existing version or ledger row may be edited.

| Object                       | Exact proposed contract                                                                                                                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `public.asset.owner_id`      | UUID, nullable, no default, no identity/generated expression. Existing rows acquire NULL without assigning a user or updating any original field.                                                                                                                   |
| `asset_owner_id_fkey`        | FK `(owner_id)` to `public.app_user(id)`, `MATCH SIMPLE`, `ON DELETE RESTRICT`, `ON UPDATE NO ACTION`, non-deferrable, initially immediate, validated and enforced.                                                                                                 |
| `asset_owner_created_id_idx` | Non-unique ordinary B-tree `(owner_id ASC NULLS LAST, created_at DESC NULLS FIRST, id DESC NULLS FIRST)`, default operator classes, valid/ready, no predicate, expression or INCLUDE columns. The explicit NULL orders match ordinary PostgreSQL ASC/DESC defaults. |
| `asset_owner_required_check` | Enforced `CHECK (owner_id IS NOT NULL) NOT VALID`, explicitly approved. Leave unvalidated on fresh and upgraded installations for one predictable M11 catalog contract.                                                                                             |

Preserve UUID primary key `asset_pkey`, all six original column definitions including INTEGER `size` and TIMESTAMPTZ `created_at`, original IDs, filenames, paths, timestamps and row count. No media moves, timestamp conversion, first-admin assignment, trigger, RLS or extra ownership fields. Disabled users retain their assets; the FK prevents account deletion while owned assets reference it. No account-deletion API is added.

### Why the additional check was accepted

PostgreSQL supports a constraint that skips checking pre-existing rows but enforces subsequent inserts and updates. Thus an unvalidated check can reject new NULL owners while keeping legacy NULL rows. It also rejects an unrelated update to an ownerless row unless that update supplies an owner. Approved NULL-to-owner mapping remains possible. This is a deliberate write restriction, not a timestamp-based distinction between old and new rows. See [PostgreSQL 18 ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html).

The column remains nullable; do not set NOT NULL, validate this check automatically, or infer that no NULLs remain. Restore procedures must account for restoring legacy NULL rows before the check is installed; rehearse the actual backup/restore tooling. A later approved version can validate/convert only after complete, evidence-backed mapping. An exact M11 inspector must recognize this one intentional unvalidated check while rejecting other unvalidated or non-enforced constraints. Manual catalog changes, including unsolicited validation, are drift requiring review.

Application-only enforcement was considered and rejected because it permits accidental ownerless inserts by alternate writers. Triggers or a legacy flag add unnecessary state. Neither FK nor CHECK proves the uploader's identity, forbids a privileged SQL reassignment, or provides read authorization. A mandatory non-null application insertion type and scoped queries remain required.

Kysely reads represent `owner_id: string | null`; the application create input must override that general table type with a required `owner_id: string` derived from the actor. No optional owner, caller-provided UUID or default owner in repository/service signatures. Public asset DTO fields remain unchanged; do not expose `owner_id` or `storage_path` merely because they are stored.

## 3. Migration and readiness contract

### History-first validation

Retain PostgreSQL 18, `public`, connection configuration, advisory lock and Kysely lock protections. Validate metadata table shape, keys, lock row and ordered known ledger prefix before dispatching the asset inspector. Malformed metadata must not be interpreted as an empty installation. Keep status read-only. No production-only validation bypass.

| Valid history                                                                                                                            | Required catalog and action                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| No history, no managed relations                                                                                                         | Fresh install; reject reserved-name collisions; apply M8 → M10 → M11. Valid empty Kysely bootstrap metadata is still allowed.    |
| No history, exact legacy asset only                                                                                                      | Require existing explicit `--baseline-legacy`; unchanged M8 baseline records history without rewriting rows; apply M10 then M11. |
| M8 only                                                                                                                                  | Exact historical asset; auth and ownership objects absent; apply M10 then M11.                                                   |
| M8 + M10                                                                                                                                 | Exact historical asset and M10 auth; ownership objects absent; apply M11 only.                                                   |
| M8 + M10 + M11                                                                                                                           | Exact M11 asset and unchanged M10 auth schema; repeat invocation makes no changes.                                               |
| Any gap, unknown/out-of-order version, invalid timestamp, partial metadata, missing managed relation or schema inconsistent with history | Safe nonzero refusal; no baseline, recreation, ledger repair or guessed ownership.                                               |

Before M11 is applied, use the frozen M8 inspector and reject ownership columns/constraints/reserved names. After M11, use a new exact `asset-ownership-schema.ts` inspector. It validates the six old columns plus nullable UUID owner, exact PK/FK/index/check definitions and enforcement/validation flags; reject extra columns/defaults/indexes, wrong targets/actions/order, custom triggers/rules, RLS, inheritance, partition/view substitutions and partial objects. Keep `legacy-asset-schema.ts`, `auth-schema.ts` and both historical version files behaviorally frozen.

The new version rechecks M10 prerequisites inside Kysely's transaction, rejects collisions, adds only the approved delta and validates the result before returning. Use transactional ordinary index creation, not `CREATE INDEX CONCURRENTLY` inside the transaction. Locks and index work may block writers; use a maintenance window and existing bounded CLI timeouts. Failure rolls back pending DDL/ledger entries; metadata bootstrap may remain as documented by M8. Do not change timeout defaults or introduce retries that repair schema silently. Repeat and concurrent invocations retain runner serialization. `down()` must refuse destructive ownership removal.

11B/11C application composition stays locked and can recognize the new schema through the updated runner while retaining M10 readiness requirements. **Before mounting routes in 11D**, startup must additionally require an applied M11 version and exact M11 schema. A pre-M11 database must fail before listening; no startup migration. Status/CLI must continue recognizing supported earlier states for explicit upgrades.

### Compatibility and real-data gate

M10 binaries reject the extra column under their strict validator. No mixed M10/M11 rolling rollout or assumption that additive DDL permits code rollback. Stop old writers, apply the reviewed upgrade explicitly, then start matching code. M11 checkpoint builds through 11C do not reopen media. A failed upgrade/startup requires reviewed forward repair or restore, not dropping ownership or deleting ledger rows. Kysely records version names/timestamps, not source checksums; diff review enforces historical immutability.

This phase never connects to the development database. Before any real baseline/upgrade: obtain separate maintainer approval, matching PostgreSQL/media backups with verified restore capability, actual schema/history review and isolated rehearsal. Verify synthetic/restored row snapshots, IDs, paths, timestamps, ownership NULLs and history before/after. Media verification requires its own authorization; 11A does not inspect photographs. Preserve existing Docker volumes. No schema spec or passing disposable test authorizes a real upgrade.

## 4. API and authorization contract

Every asset route requires an active, unrestricted browser session. Actor identity comes only from server session resolution. Reuse M10 cookie names/attributes, exact `APP_ORIGIN`, unsupported-credential rejection, default-deny guard and CSRF. No native bearer support or administrator exception.

| Caller/resource                                                                                                   | Result                                                                  |
| ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Missing, invalid, expired, revoked or disabled-account credentials; unsupported Authorization/Proxy-Authorization | Fixed 401; no asset lookup or storage work                              |
| Valid restricted first-login session                                                                              | Fixed 403; no asset work                                                |
| Active unrestricted user/admin accessing own resource                                                             | Normal successful response                                              |
| Foreign, NULL-owned or absent valid UUID                                                                          | Same 404 `{statusCode:404,message:"Asset not found",error:"Not Found"}` |
| Malformed UUID after successful authentication                                                                    | Fixed 400 using existing UUID validation/error sanitization             |
| Invalid/missing/null Origin or invalid CSRF on unsafe request                                                     | Fixed 403 before multipart processing                                   |
| Authentication database unavailable                                                                               | Sanitized 503, no asset work                                            |

Authorization precedes resource validation, so anonymous malformed IDs do not disclose route/resource details. All asset responses/errors use `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Errors use the existing fixed envelope; no SQL, path, filename, cookies, tokens or raw framework text in diagnostics. Equal denials mean equal status/message/header policy and no file access; do not promise constant-time database behavior or identical transport-generated headers.

| Route                                                        | Proposed behavior                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/assets` and trailing slash                      | 200 array of existing DTOs, only `WHERE owner_id = actor.userId`; order `created_at DESC, id DESC`. Empty own gallery is `[]`. Keep current unpaginated contract; record bounded-list work as later scope.                                                                                                                                                                         |
| `POST /api/v1/assets/upload`                                 | Existing one multipart `file` part, 20 MiB limit, no form fields; success 201 existing DTO. Owner form fields are rejected by current field limit; arbitrary owner headers/query values confer no authority and are never passed into create.                                                                                                                                      |
| `GET /api/v1/assets/:assetId`                                | 200 existing DTO only from `WHERE id = :id AND owner_id = :actorId`.                                                                                                                                                                                                                                                                                                               |
| `GET /api/v1/assets/:assetId/original`                       | Scoped file-record query first, then existing safe open; original bytes/MIME/length and inline disposition preserved.                                                                                                                                                                                                                                                              |
| `GET /api/v1/assets/:assetId/thumbnail`                      | Same scope-first rule, then JPEG thumbnail stream.                                                                                                                                                                                                                                                                                                                                 |
| HEAD for GET routes                                          | Same auth/scoping and status/header policy, no body; Fastify fallback must not bypass lookup. Unauthorized HEAD must not open storage.                                                                                                                                                                                                                                             |
| Range on original/thumbnail                                  | Same authorization first. Retained controller has no explicit partial-content implementation. | Encoded segments, trailing slashes, unknown subpaths/methods | Any alias dispatched to an asset handler must take identical auth/scoped paths. Early namespace detection must agree with the actual Fastify router for encoded separators/segments and trailing slashes. Test aliases rather than assuming one `decodeURIComponent` matches routing. Unrecognized/double-encoded forms may safely remain unavailable; no alias needs to be newly supported. Unsafe recognized namespace requests require Origin/CSRF even if no route exists. Keep the Nest guard for real routes as defense in depth; an early cached actor must not silently become durable authorization.

All repository read signatures require owner; SQL contains the predicate, never fetch-all/filter-in-memory. Missing, foreign and ownerless rows short-circuit before `openOriginal`, `openThumbnail` or filesystem existence checks. Missing files for an authorized owned row may retain the existing sanitized file-not-found response. Before-header stream errors clear stale media headers and return JSON; after-header errors terminate the response, preserving the M9 correction. No static media route, redirect or path-based alternate access.

## 5. Upload transaction and concurrency contract

### Ordered workflow

1. Early authentication rejects invalid/restricted credentials and enforces exact Origin/CSRF before multipart parsing. The controller obtains a typed actor; no body-selected owner.
2. Keep existing streaming/backpressure, filename/MIME/20 MiB checks, full multipart completion, 40-million-pixel/single-page Sharp safeguards and thumbnail generation. Stage/publish through existing no-overwrite storage. No database transaction or row lock during stream consumption or Sharp work.
3. After successful publication, begin a short PostgreSQL READ COMMITTED transaction using the existing pool. Lock `app_user` by actor user UUID with `FOR UPDATE`; revalidate active and unrestricted state. Then lock `auth_session` by **both** actor session UUID and user UUID with `FOR UPDATE`. Missing/deleted session or inactive user is 401; a still-valid restricted account is 403. Read current rows, not the actor snapshot alone.
4. After both locks are acquired, compare session expiry with database `clock_timestamp()` in a separate final check immediately before insertion. Do not use JavaScript receipt time or transaction-start `CURRENT_TIMESTAMP` across a lock wait. Insert only through that transaction with the server user UUID. Require a matching row and a successful insertion; never fall back to a pool-level insert.
5. Hold both locks until commit/rollback. Send 201 only after commit success, preserving the public DTO. An expired session at the final check prevents insertion; natural expiry after that check does not retroactively cancel the short transaction. No automatic transaction replay after uncertain commit.

PostgreSQL distinguishes transaction-start time from wall-clock time; see [date/time functions](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT). A pool or lock wait can span session expiry. A timeout/deadlock is a safe failed upload, not permission to skip revalidation.

### Serialization with inspected M10 operations

| Competitor                                | Existing locking and proposed upload outcome                                                                                                                                                                                                                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Logout                                    | Deletes current session without first locking user. Upload's session lock serializes the delete. Delete commits first → missing session, no insert; upload holds session first → delete waits until upload completes. Logout never waits for a user lock while holding session, so this path introduces no inverse cycle.      |
| Logout-all / individual revoke            | Locks/updates user before deleting sessions. If that transaction commits first, upload cannot revalidate the deleted session. If upload holds user first, revocation waits. Preserve logout-all's monotonic `updated_at` revision and login comparison.                                                                        |
| Password change / local password recovery | User lock then password change/session deletion. Same ordering; recovery winning forces upload rejection. No password verification or hashing is added to upload.                                                                                                                                                              |
| Administrator disable                     | Existing advisory transaction lock, administrator row, target user row, then target sessions. Upload locks only its own user/session and never requests that advisory lock or another user row. A committed disable before final authorization denies upload; upload winning may commit, then disable preserves its ownership. |
| Login / concurrent uploads                | Login locks user before session issuance; uploads each lock their own user then session. Same-user uploads serialize only their short final transactions; distinct generated asset UUIDs and no-overwrite publication remain. No global upload lock.                                                                           |
| Session expiry/pruning                    | Final wall-clock expiry test is required even if the row still exists. Pruning deletes expired sessions without acquiring user afterward; session row lock serializes it. No cached expiry acceptance after a wait.                                                                                                            |

Authorization ordering is established by the final locked state/expiry check; durable visibility is established by commit. A competing revocation that is ordered first and commits prevents upload. A revocation that rolls back does not. Upload winning the locks may complete even if the revocation request arrived earlier. Commit acknowledgement loss must not be interpreted as rollback. Read/stream requests keep M10's request-time authorization limit: already-authorized bytes cannot be recalled, and open streams may finish after revocation. Future requests must reject revoked credentials.

These are source-derived lock-order arguments, not executed M11 concurrency results. 11C must prove both orders with deterministic barriers/independent connections, bounded test timeouts and no sleep-based race assumptions. Do not refactor unrelated account operations or change M10 schema to implement this policy.

## 6. Compensation and filesystem consistency

The existing broad `catch → deleteImage` must not survive unchanged around a transactional create. The repository/transaction boundary must make commit phase and certainty explicit to the service; a generic rejected Promise is insufficient evidence. Keep HTTP error mapping separate from the internal persistence outcome.

| Observed outcome                                                                                     | Required handling                                                                                                                                                                                         |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage fails before returning successful publication                                                | Preserve storage's per-attempt publication tracking and temporary cleanup. Never delete a colliding pre-existing file. No metadata insert attempted.                                                      |
| No transaction/insert attempted, or final authorization rejected before insert                       | Metadata cannot exist for this attempt. Attempt cleanup of only the successfully published files belonging to this newly generated UUID.                                                                  |
| Insert/transaction failed with confirmed abort, or rollback acknowledged before COMMIT was attempted | Cleanup permitted for this attempt only. A rollback/transport error that obscures the phase must not be guessed safe.                                                                                     |
| COMMIT may have been sent and fails/times out/loses acknowledgement, or phase cannot be proven       | Outcome unknown. **Retain both published files**, return sanitized failure, emit an allowlisted diagnostic with generated correlation/asset UUID only. Do not delete, retry insertion, or claim rollback. |
| Commit acknowledged, later serialization/response/socket failure                                     | Retain files and row. The client may not know it succeeded; later own listing can reveal it. No rollback or cleanup after commit.                                                                         |

The installed Kysely scoped `transaction().execute()` implementation commits only after its callback returns; on failure it attempts rollback, including after a failed COMMIT. Thus even a successful subsequent ROLLBACK cannot prove that an earlier COMMIT did not succeed. Keep the scoped API for pool/connection lifecycle and add a small per-attempt outcome wrapper: track whether the callback completed, use a private failure marker for a callback abort, and classify a marker rethrown after the scoped transaction finishes as confirmed rollback only when the library's rollback-success semantics have been verified. Rollback failure replaces that error in the inspected implementation and must be classified as unknown. Any failure after callback completion is conservatively unknown, irrespective of a later rollback response. No raw SQLSTATE shortcut or new framework is needed.

11C must test these boundaries against the installed Kysely version and verify connection release under failures; re-review on dependency changes. A typed marker from an ordinary insert exception alone, before the transaction wrapper finishes, is insufficient. If outcome evidence is unavailable, retain files. A subsequent missing row from another connection is not proof that an in-flight commit cannot finish; no destructive reconciliation on that basis. Do not use manually controlled transactions merely for phase visibility if that introduces connection leaks on failed commit/rollback.

An acknowledged rollback permits best-effort cleanup but does not guarantee it succeeds. Failed cleanup is safely logged and leaves a private orphan. Keep UUID paths, `wx` staging, 0600 permissions, original-byte preservation, symlink protections and no-overwrite links. Never sweep unrelated files, legacy paths or other users' media. No directory-per-owner redesign.

This design avoids deliberate deletion on ambiguous commit but does not provide PostgreSQL/filesystem atomicity, fsync durability, full crash recovery or exactly-once client retries. Crashes can leave temp files, one published file or orphan files; a client retry can create a duplicate under another UUID. Scoped metadata retrieval prevents HTTP access to orphans. Failure injection for the changed compensation boundary is mandatory; comprehensive filesystem write/cleanup injection, reconciliation and NAS/privileged-directory races remain separate limitations.

## 7. Production reopening and legacy policy

11B adds schema only, with existing blanket lockdown. 11C changes isolated core/tests only; `AppModule` still omits assets and the early hook still returns M10's fixed responses. 11D replaces that hook with early authenticated/unrestricted/Origin/CSRF enforcement, mounts scoped assets, requires M11 readiness and updates production-composition tests **as one reviewed security boundary**. Never mount legacy unscoped code even temporarily. No development bypass, feature flag, static mount or admin escape hatch.

`GET /api/v1/me` continues reporting `assetsAvailable:false` through 11C. In completed 11D it may report true for an active unrestricted actor only; restricted sessions remain false. This signals capability, not gallery contents. Keep localhost defaults; reopening application routes does not approve public exposure or deployment.

**Optional 11E is deferred by maintainer decision.** M11 can serve newly uploaded owned media while older NULL-owned photographs remain quarantined. No first-admin assignment, filename/path/time inference, image scan, automatic backfill or cleanup. Ownership mapping is not a schema migration and is not a prerequisite to safely serving new owned rows.

If later approved, a standalone operator tool needs an evidence-backed asset-ID → active-user-ID manifest, dedicated confirmed target configuration, dry run, bounded all-or-nothing transaction and `owner_id IS NULL` compare-and-set. Reject duplicate/conflicting/missing IDs and changed state; report only selected IDs/outcomes without paths. Lock/revalidate target users before assets in deterministic order. Change only selected NULL owner values, never existing owners, metadata or files. Verification of provenance, backups and actual execution each require separate approval; no mapping command is authorized here.

## 10. Approved decisions, execution gates and limitations

The maintainer approved these architectural decisions on 2026-10-23:

1. Nullable ownership, exact FK/index/version and the enforced NOT VALID check, including its restriction on legacy updates and restore implications.
2. Owner-only SQL/HTTP policy, no admin bypass, restricted 403, shared asset 404, full-response Range policy and unchanged successful DTO.
3. User-then-session final transaction, post-lock wall-clock expiry and documented revocation/in-flight linearization.
4. Conservative file retention on unknown commit and mandatory focused failure tests; no broad cleanup or claim of atomicity.
5. Deferral of 11E, leaving legacy photos quarantined; no transfer/sharing/Family Space in M11.
6. Phase sequencing and explicit 11D reopening review, plus maintenance-window compatibility and separate real-upgrade gates.

The architectural approval does not start 11B. Each implementation phase, real-data migration, production route reopening review, deployment and merge retains the separate gates described above. Production still runs M10's blanket asset lockdown; no ownership migration has been executed on the development database.

Family Space, shared albums/direct sharing, ownership-transfer UI, mobile native authentication, Redis/BullMQ, Python ML/face recognition, asset deletion/trash/recovery and full deployment are out of scope. Future sharing should add explicit grants/membership independently of owner identity and timeline/retention policy. No speculative fields are needed now.

Remaining risks include in-flight streams after revocation; ambiguous client outcomes/duplicate retries; orphan files, failed cleanup and no complete crash recovery; incomplete general filesystem failure injection; unpaginated lists and no new upload concurrency/CPU quota; single-process auth throttling; trusted operator and credential-delivery assumptions; unverified production TLS/proxy/cookies/backup restoration. Ownership is necessary but does not make the application production-ready.
