# M12C storage provenance — operator notes

**Status:** Draft operational notes. A fresh-only `storage:provision-fresh` command exists and focused native ext4 tests passed on a disposable GitHub-hosted runner, but the command is not approved for real-data use. Historical-adoption inventory assessment is read-only; adoption, relocation and restoration have no executable cutover command. M12B still refuses HTTP startup for an applied M12 schema.

The approved [M12 specification](milestone-12-spec.md#12-binding-identity-adoption-and-restoration) requires a database-wide logical binding and separate physical identity evidence for originals and thumbnails. Marker version 2 records each role's logical IDs, ext4 filesystem UUID, opaque directory handle and application-visible location fingerprint. Ordinary startup never creates or repairs markers. Configured paths and copied markers cannot establish provenance.

Before a future operator procedure may be used, it must verify the actual database/media pair, document a complete inventory and backup/restore plan, stop and fence writers, observe both directories under the intended unprivileged runtime, and positively confirm the singleton transaction's outcome. An approved location change requires a complete verified copy and explicit marker re-establishment while retaining the same database logical IDs. Restoring onto a different directory or filesystem likewise needs matched snapshot evidence and controlled physical identity re-establishment. Keep the pairing and recovery record protected outside both media roots and include it in backups; it is not a second runtime authorization file.

Missing mounts, unavailable identity observation, mismatched markers and uncertain commits leave media unavailable. Metadata-only access may remain possible under the normal owner and session checks once a reviewed M12 runtime exists. Never infer file absence from an unverified directory or remove media while the binding is uncertain.

The Linux helper source is `server-nest/native/storage-identity-observer.c`. On Linux, `npm run build` compiles it to `server-nest/dist/native/storage-identity-observer` using `cc`, libc and installed Linux UAPI headers. The Node adapter opens a role directory without following its final symlink, passes only that opened directory as inherited fd 3, and accepts bounded JSON evidence from the helper. The helper checks ext4, obtains the filesystem UUID with `FS_IOC_GETFSUUID`, obtains an opaque handle with `name_to_handle_at(..., AT_EMPTY_PATH)`, and opens the marker relative to the same descriptor. Unsupported calls, missing markers, stale paths and malformed output fail closed. No path argument or privileged `open_by_handle_at` operation is accepted. `npm run test:native` currently proves protocol bounds and non-ext4 rejection only; it does not certify ext4.

The focused [hosted ext4 run](https://github.com/saefr-app/saefr-photos/actions/runs/40367223110) passed identity, exact-byte upload/read/removal, normal unmount/remount, missing/swapped mounts and non-root container checks on disposable images; the cleanup log confirms both mounts and images were removed. This host has no usable `/dev/kvm` or prepared disposable guest image; no local host loop device or `/boot` test was attempted. Process-crash, power-loss and full operator cutover behavior remain unverified. Do not use these notes to adopt development storage or migrate an existing installation.

The synthetic fresh-install primitive requires both role directories and all three relevant database tables to be empty, writes markers exclusively and syncs them before a short singleton transaction, then verifies the binding. It never repairs a partial marker write. The separate interactive CLI requires `STORAGE_OPERATOR_POSTGRES_HOST`, `PORT`, `DB`, `USER`, `PASSWORD` and `STORAGE_OPERATOR_ROOT`, plus exact `--confirm-database` and `--confirm-root` arguments. It checks the complete M12 migration history, generates new logical IDs and prints them only after verified completion; it does not load ordinary application credentials or run on HTTP startup. It has **not** been run on existing data. The command does **not** establish historical media provenance and must not be used for an existing installation. Real use still requires native certification, a reviewed configuration and backup plan, stopped writers and separate approval.

The read-only `assessHistoricalAdoption` preflight requires an operator-reviewed manifest naming the approved historical originals roots and SHA-256 digests for every original and thumbnail. Against a stopped synthetic installation, it checks every database asset row, canonical target names, byte sizes and hashes, both complete role inventories and native role observation. It rejects missing, additional or symlinked files. A passing preflight does not insert `storage_binding`, create markers, fence writers, establish human-reviewed provenance or authorize real adoption. It must be rerun after any data or storage change; a separate reviewed transaction/cutover procedure remains required.

For relocation, stop and fence all storage-capable processes, verify a complete copied inventory for each role, then re-establish each moved marker with fresh physical identity and the approved new location fingerprint while preserving database logical IDs. For restoration, verify the database/media snapshot pair and pending deletion receipts before re-establishing physical markers at any changed location. Do not copy an old marker as proof or rewrite the database anchor. Neither procedure has an executable command in M12C; interrupted or uncertain cutovers remain unavailable pending operator review.
