# M12C storage provenance — operator notes

**Status:** Draft operational notes. Interactive fresh provisioning, historical adoption and controlled location re-establishment primitives exist and are tested only with disposable PostgreSQL and synthetic files. None is approved for real-data use. The production `main.ts` startup gate still refuses M12 schema pending independent review.

The approved [M12 specification](milestone-12-spec.md#12-binding-identity-adoption-and-restoration) requires a database-wide logical binding and separate physical identity evidence for originals and thumbnails. Marker version 2 records each role's logical IDs, ext4 filesystem UUID, opaque directory handle and application-visible location fingerprint. Ordinary startup never creates or repairs markers. Configured paths and copied markers cannot establish provenance.

Before a future operator procedure may be used, it must verify the actual database/media pair, document a complete inventory and backup/restore plan, stop and fence writers, observe both directories under the intended unprivileged runtime, and positively confirm the singleton transaction's outcome. An approved location change requires a complete verified copy and explicit marker re-establishment while retaining the same database logical IDs. Restoring onto a different directory or filesystem likewise needs matched snapshot evidence and controlled physical identity re-establishment. Keep the pairing and recovery record protected outside both media roots and include it in backups; it is not a second runtime authorization file.

Missing mounts, unavailable identity observation, mismatched markers and uncertain commits leave media unavailable. Metadata-only access may remain possible under the normal owner and session checks once a reviewed M12 runtime exists. Never infer file absence from an unverified directory or remove media while the binding is uncertain.

The Linux helper source is `server-nest/native/storage-identity-observer.c`. On Linux, `npm run build` compiles it to `server-nest/dist/native/storage-identity-observer` using `cc`, libc and installed Linux UAPI headers. The Node adapter opens a role directory without following its final symlink, passes only that opened directory as inherited fd 3, and accepts bounded JSON evidence from the helper. The helper checks ext4, obtains the filesystem UUID with `FS_IOC_GETFSUUID`, obtains an opaque handle with `name_to_handle_at(..., AT_EMPTY_PATH)`, and opens the marker relative to the same descriptor. Unsupported calls, missing markers, stale paths and malformed output fail closed. No path argument or privileged `open_by_handle_at` operation is accepted. `npm run test:native` currently proves protocol bounds and non-ext4 rejection only; it does not certify ext4.

The focused [hosted ext4 run](https://github.com/saefr-app/saefr-photos/actions/runs/40367223110) passed identity, exact-byte upload/read/removal, normal unmount/remount, missing/swapped mounts and non-root container checks on disposable images. A [follow-up run](https://github.com/saefr-app/saefr-photos/actions/runs/40369514754) killed the provider process after link creation but before directory-sync acknowledgement; the original and staging link remained for explicit reconciliation. Both runs logged removal of their disposable mounts and images. This host has no usable `/dev/kvm` or prepared disposable guest image; no local host loop device or `/boot` test was attempted. Full database/FS crash recovery, VM power-loss and operator cutover behavior remain unverified. Do not use these notes to adopt development storage or migrate an existing installation.

The synthetic fresh-install primitive requires both role directories and all three relevant database tables to be empty, writes markers exclusively and syncs them before a short singleton transaction, then verifies the binding. It never repairs a partial marker write. The separate interactive CLI requires `STORAGE_OPERATOR_POSTGRES_HOST`, `PORT`, `DB`, `USER`, `PASSWORD` and `STORAGE_OPERATOR_ROOT`, plus exact `--confirm-database` and `--confirm-root` arguments. It checks the complete M12 migration history, generates new logical IDs and prints them only after verified completion; it does not load ordinary application credentials or run on HTTP startup. It has **not** been run on existing data. The command does **not** establish historical media provenance and must not be used for an existing installation. Real use still requires native certification, a reviewed configuration and backup plan, stopped writers and separate approval.

The read-only `assessHistoricalAdoption` preflight requires an operator-reviewed manifest naming the approved historical originals roots and SHA-256 digests for every original and thumbnail. Against a stopped synthetic installation, it checks every database asset row, canonical target names, byte sizes and hashes, both complete role inventories and native role observation. It rejects missing, additional or symlinked files. A passing preflight does not insert `storage_binding`, create markers, fence writers, establish human-reviewed provenance or authorize real adoption.

The separate `storage:adopt-historical` command requires a mode-0600 JSON evidence file owned by the operator process UID **outside** the media root. The exact top-level keys are `version: 1`, `databaseName`, canonical `storageRoot`, `backupRecordSha256`, and `manifest`. The manifest is the full reviewed preflight manifest. The operator supplies the independently reviewed backup-record digest as `STORAGE_OPERATOR_BACKUP_RECORD_SHA256`, the file path as `STORAGE_OPERATOR_EVIDENCE_PATH`, separate `STORAGE_OPERATOR_POSTGRES_*` credentials, and exact `--confirm-database`, `--confirm-root`, `--confirm-services-stopped`, and `--confirm-backup-record` arguments. The command checks a TTY and migration history, reruns the complete inventory, observes both physical roles, creates markers exclusively, rechecks identities, then inserts the singleton under a short table lock. An uncertain COMMIT is accepted only after independent exact-tuple confirmation. The command cannot prove services are stopped or a backup exists; those are operator-reviewed prerequisites. Partial marker writes remain in place for investigation and cannot be retried as a fresh adoption with new IDs.

For relocation, stop and fence all storage-capable processes and drain outstanding I/O. Keep the old location offline. Verify a complete copied inventory for each role before cutover. For restoration, verify the database/media snapshot pair and reassess every pending or completed deletion receipt. A pre-M12 restore requires migration and explicit historical adoption instead. Do not copy an old marker as proof or rewrite the database anchor, asset rows or journal targets.

The `storage:reestablish-location` command requires the same separate operator credentials, TTY, evidence path, backup digest and exact confirmations as adoption. It additionally requires `STORAGE_OPERATOR_STORAGE_ID`, `STORAGE_OPERATOR_ORIGINALS_BINDING_ID` and `STORAGE_OPERATOR_THUMBNAILS_BINDING_ID` copied from the reviewed existing database binding. The protected evidence file must have exact top-level keys `version`, `databaseName`, `storageRoot`, `backupRecordSha256`, `binding` (`storageId`, `originalsBindingId`, `thumbnailsBindingId`), `assetRowsSha256`, `deletionRowsSha256` and `files`. The two row digests are SHA-256 of JSON serialization of complete `asset` rows ordered by `id` and complete `asset_deletion` rows ordered by `asset_id`, including pending and completed receipts. Each `files` entry has `role`, `name`, `size` and `sha256`; it inventories **every** regular managed file in both roles, including explicit staging residue. Both destination marker names must be absent. The verifier checks exact SQL digests and binding, every file's size/hash, active asset originals/thumbnails, completed-deletion absence and unchanged SQL after the scan. It observes both destination roles, exclusively creates and syncs new markers with the unchanged logical IDs, rechecks SQL and both physical roles, then verifies the resulting binding. A copied marker, extra file, mismatched database/media pair, changed receipt, missing target or partial prior cutover fails closed. It never deletes files or mutates SQL.

The protected evidence is an operator-reviewed backup and pairing record, **not** a runtime authority or a substitute for an independently verified backup. The confirmation flags are attestations, not mechanical process fencing. Failed or interrupted marker creation leaves any partial markers untouched; do not rerun until the exact state has been reviewed and a recovery plan approved. These synthetic-tested primitives do not authorize using the commands on the development installation or any real media. Native relocation/restoration, reboot and power-loss cutover tests remain outstanding.
