# Milestone 11 planning draft — Asset Ownership and Authorization

**Status: historical planning draft, superseded by the approved Phase 11A contract; M11 is not implemented.** Based on merged `integration` commit `acf6ed44bb870fdae56e68c523ba660af6536897` and [M10 post-merge verification](milestone-10-postmerge-report.md). The maintainer approved the detailed [M11 specification](milestone-11-spec.md) and [ADR 0005](../decisions/0005-asset-ownership.md) on 2026-10-23 after independent review. The historical proposal language below records the planning process; the approved documents control implementation. No database migration, media operation or route reopening is authorized here.

## 1. Current contracts and threat boundary

The legacy `public.asset` table has UUID `id`, `filename`, `mime_type`, INTEGER `size`, `storage_path` and `created_at` (`timestamptz`), all NOT NULL and without defaults. It has no owner. M8's `202610170001_initial_asset` and M10's `202610210001_authentication_foundation` are applied through the standalone Kysely runner; neither is to be edited. The strict current-state validator still expects the exact historical asset table. `app_user.id` is the existing user UUID, and `auth_session` supplies revocable browser sessions.

The retained `AssetsController`/`AssetsService`/`AssetsRepository` provide upload, list, metadata and original/thumbnail streams, but production `AppModule` omits `AssetsModule`; the early Fastify hook blocks the entire asset namespace. The retained repository currently queries assets without an owner predicate. Storage uses UUID-derived filenames in shared `originals/` and `thumbnails/` directories, validates legacy path basename, and opens files with `O_NOFOLLOW`. Its upload stages private files, checks multipart completion, format, size and pixel limits, then publishes with no-overwrite hard links before the database insert. It attempts cleanup on failure but database and filesystem changes are not atomic.

M11 protects one application user from another and from an administrator browsing their media. The host operator remains trusted and can access the database/files directly. **No M11 intermediate runnable composition may combine mounted asset routes with unscoped asset queries.** Ownerless rows stay inaccessible until an explicit, reviewed mapping is applied. Existing IDs, paths, timestamps and files must not be rewritten merely to add ownership.

## 2. Recommended ownership model

User deletion cannot orphan owned assets. A disabled user retains ownership but cannot authenticate. |

Require a non-null owner in the TypeScript service/repository insertion contract. | The nullable database column is a transitional legacy accommodation, not permission for new ownerless application uploads.                    |
| Role        | An administrator and an ordinary user may access only assets they own. The approved migration identifier is `202610220001_asset_ownership` (no conflict found at the inspected merge; recheck before implementation). Preserve `size` as INTEGER and `created_at` as `timestamptz`; no unrelated conversion or media move. The approved contract adds `asset_owner_required_check CHECK (owner_id IS NOT NULL) NOT VALID`. This enforced check preserves existing NULLs but rejects subsequent NULL inserts and updates, including unrelated updates to legacy ownerless rows. Keep the column nullable and the check unvalidated in fresh and upgraded M11 schemas. A later version may validate/set NOT NULL only after approved complete mapping and rehearsal. The prior draft's claim that PostgreSQL could not distinguish existing NULLs from new NULL writes was too broad; the check supplies a write boundary without a new marker or trigger. See the specification for exact catalog, restore and application identity constraints.

## 3. Migration history, upgrade and recovery

1. **Historical state:** With no M11 ledger version, preserve the frozen M8 asset inspector and M10 auth inspector. An unexpected `owner_id` or reserved FK/index name before the M11 version is a partial/incompatible schema and must fail; do not silently baseline it.
2. **Version registration:** Append the M11 file to `migration-provider.ts`. Do not rename or edit either historical version, hand-write ledger rows or add startup migration. The explicit CLI and its `MIGRATION_POSTGRES_*` confirmation remain mandatory.
3. **Version `up`:** Within Kysely's PostgreSQL migration transaction, verify the managed M10 state, reject collisions, add nullable `owner_id`, FK and index, then inspect the completed M11 catalog before Kysely records the version. A failed transaction must roll back DDL and ledger entry.
4. **Current-state validation:** `migration-runner.ts` currently calls `inspectLegacyAsset()` before reading history, so an M11 column would make post-upgrade status/startup fail. Reorder preflight safely to validate metadata/history first and dispatch by applied version: frozen M8 asset contract when M11 is absent; a new exact M11 catalog inspector when it is present. M10 auth validation stays history-aware. The new inspector must validate the original six columns and constraints plus the exact M11 delta, reject missing/extra columns, wrong FK actions, index shape, defaults, triggers/RLS and damaged history. There is no production-only bypass.
5. **Installation paths:** Fresh disposable installations apply M8, M10, M11 in order. Managed M10 installations apply only M11. A compatible untracked SQLModel asset table still requires the existing explicit M8 `--baseline-legacy` path before M10 and M11. Repeated and concurrent runs must be safe and idempotent. Partially installed or incompatible installations fail with a clear non-destructive error.
6. **Real-data gate:** No command in this plan runs on the development database. Before any real upgrade, obtain separate approval; verify matching PostgreSQL and media backups and restore capability; inspect actual schema/history; rehearse on a disposable restored copy; record row count, IDs, paths and content checks before/after; use a maintenance window. M10 API code may reject the additive M11 schema under its strict validator, so avoid mixed-version rollout. On failure, stop and use a reviewed restore or forward-repair plan. Automatic `down` must refuse data-destructive rollback; adding a nullable column does **not** make code rollback automatically safe.

The legacy owner mapping is **not** a schema migration. It requires evidence identifying the rightful user for each selected asset, explicit operator approval and a separate tool/phase; unmapped records remain NULL and inaccessible. Do not scan photographs or infer ownership from file paths. The maintainer deferred optional 11E: new owned galleries can work without exposing or mapping older photos.

## 4. HTTP and authorization contract proposal

Preserve successful asset response shapes and original bytes. Use the current browser session model, default-deny guard, exact Origin and CSRF for uploads; do not add native bearer transport. Require a normal active session with `passwordChangeRequired=false` for every asset operation. Admins satisfy the same owner rule as ordinary users. Anonymous requests remain 401; restricted sessions receive a fixed 403. For a syntactically valid UUID, both an unknown asset and another user's or ownerless asset return the **same sanitized 404** with no storage access. Malformed UUIDs may continue to receive the existing fixed 400, independent of whether a row exists. Avoid response-size, error text, timing or header differences that reveal another user's file where practicable.

| Operation                                                  | Required server-side predicate and behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| List `GET /api/v1/assets` (with or without trailing slash) | Query `WHERE owner_id = actor.userId` in `AssetsRepository`; never fetch all and filter in memory. Preserve the current response shape/order; pagination is a separate milestone.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Upload `POST /api/v1/assets/upload`                        | Authorize before multipart consumption; pass only the resolved actor to `AssetsService`; insert its UUID as owner. Immediately before metadata insert, revalidate active user, unrestricted current session and expiration in a transaction, locking the user row and then the current session row (`FOR UPDATE`) before insertion. This order serializes with disable, password change, logout-all, individual revocation and logout; a concurrent session DELETE must wait for the locked row. If revocation wins, reject and attempt cleanup of this upload's newly published UUID files. If upload insertion wins, later revocation blocks subsequent requests; it cannot retract an already completed upload. Keep lock ordering consistent with existing auth transactions. |
| Metadata `GET /:id`                                        | Query by `id AND owner_id`; same 404 for foreign, ownerless and absent IDs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Original/thumbnail `GET /:id/...`                          | Perform the scoped database lookup **before** calling `LocalStorageService`; never expose `storage_path` in the response. Keep existing MIME/path checks and stream failure sanitization.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| HEAD, Range and aliases                                    | Apply the same authentication and owner predicates before opening any file, including Fastify's HEAD fallback, Range requests, trailing slashes, encoded paths and unknown asset-namespace subpaths. Do not imply partial-content support unless existing behavior is verified; unauthorized Range requests must never produce bytes, range headers or distinguishable existence information.                                                                                                                                                                                                                                                                                                                                                                                     |

The M10 blanket `onRequest` lockdown must remain in place through schema and isolated-service phases. In a single reviewable composition change, replace it with an early asset-namespace authentication gate and mount `AssetsModule` only after scoped repository/service predicates and isolated negative tests pass; add mounted-route HTTP negative tests in that same composition change and pass them before review. The early gate must reject unauthenticated/restricted/unsupported credentials before multipart parsing; the Nest guard and scoped repository checks must still enforce authorization for recognized routes. Unknown aliases must fail closed. `GET /api/v1/me` may report `assetsAvailable: true` only after this complete composition is verified. A reviewed M11 change is the **only** route-reopening path; a feature flag or administrator bypass is not proposed.

A request whose session was valid at authorization time may finish after revocation, especially a stream already sending bytes. Future requests must fail. For uploads, the specification requires the final expiry check using database wall-clock time after acquiring user and session locks; transaction-start time is insufficient after a lock wait. Upload authorization is ordered at that final check, while durable visibility depends on commit. Cleanup after rejection is permitted only with a known non-commit outcome as specified below. Authorized Range requests retain full 200 responses; no partial-content feature is added. `/me` reports asset capability only for unrestricted actors after 11D.

## 5. Storage and consistency boundaries

Keep UUID-derived filenames and the existing `storage_path` column internal; do not reorganize or duplicate legacy media by owner. Scoped metadata lookup precedes every original/thumbnail `open*` call. Preserve filename/MIME checks, 20 MiB stream limits, 40-million-pixel/single-page Sharp limits, multipart-completion checks, `O_NOFOLLOW`, canonical directory checks, `wx` temporary writes and hard-link no-overwrite publication. Isolate filesystem tests under fresh temporary directories; never use the development `storage/` tree.

Owner attribution is a database fact, not a filesystem path component. Replace the existing unconditional insert-error compensation before route exposure: cleanup of this attempt's new UUID files is allowed only when metadata is known not to have committed. Retain files on uncertain commit, failed outcome classification or any failure after commit; a generic database exception or a subsequent missing-row query does not prove rollback. The specification defines the required transaction-phase evidence and targeted failure tests. Prefer a possible private orphan over deleting committed media. Process termination, filesystem failure and failed compensation can still leave metadata/files inconsistent. Avoid broad automatic cleanup; comprehensive crash reconciliation and general write/cleanup failure injection remain separate risks.

## 6. Acceptance and security tests

Use the established `npm run test:integration` and `npm run test:migrations` scripts only after their disposable PostgreSQL 18 identity, tmpfs, credentials and localhost-port checks. Use distinct users, sessions and temporary storage roots. Never migrate or point tests at the development database.

- **Migration:** fresh M8→M10→M11, managed M10→M11, explicit legacy baseline→M10→M11, repeat/concurrent execution, wrong/missing FK/index/default/type, reserved-name/partial-schema rejection, altered ledger rejection, transaction rollback, preservation of legacy row count, IDs, paths, `created_at`, and original data. Assert NULL owner for historical rows and no media operation.
- **Ownership:** user A lists/reads/streams only A's rows; user B and an administrator receive the same 404 for A's metadata, original and thumbnail as for an unknown valid UUID. Ownerless rows are absent from lists and inaccessible by ID for everyone. Disabled owners retain rows but cannot authenticate.
- **Upload:** authenticated user/admin uploads are attributed to their own UUID; forged owner fields/headers are ignored or rejected; restricted/anonymous requests never reach parser/storage; exact Origin/CSRF continue to apply. Test two concurrent uploads and unique IDs, plus disable, logout, logout-all and session-revoke races before the final insert. Assert no new NULL-owned row or foreign-owner row and preserve byte-for-byte originals.
- **Routes and streams:** real localhost socket tests cover GET, HEAD, Range, thumbnails, trailing slash, percent-encoded/unknown aliases, malformed UUID, and pre-header/after-header stream failures. Foreign/ownerless/unknown IDs must not yield body bytes, `Content-Range`, `Content-Disposition`, file size or internal paths. Preserve successful streaming behavior for the owner.
- **Failure paths:** database insert failure, interrupted/truncated multipart, invalid/oversized image, thumbnail failure and no-overwrite collision use isolated storage and remove only newly created files where possible. Record crash/uncertain-commit limitations separately; do not claim cross-system atomicity.
- **Regression:** M10 login/session/CSRF/admin and readiness suites, full build/typecheck/lint/unit/HTTP/disposable PostgreSQL/migration/runtime checks, plus a clean startup failure when the M11 schema is absent. Before any production route enablement, verify both application composition and repository predicates independently.

## 8. Historical decisions, now resolved by approved ADR 0005

1. Approve the transitional **nullable** `owner_id`, `ON DELETE RESTRICT` FK, named index, proposed version and additional enforced NOT VALID check with its legacy-update/restore restrictions; defer NOT NULL until explicit complete mapping.
2. Approve the HTTP policy: active regular users and admins see only their own assets; restricted sessions receive 403; foreign, ownerless and unknown valid IDs share one sanitized 404; malformed UUID stays 400.
3. Approve final upload-time user/session revalidation under locks in user-then-session order, post-lock wall-clock expiry, conservative retention on uncertain commit, and the documented in-flight-stream limit.
4. Decide whether the explicit operator legacy-mapping tool belongs in M11 or a later separately approved phase, and what evidence/process will establish each legacy asset's rightful owner. No default owner is safe.
5. Confirm that ownership transfer and all sharing/Family Space permissions remain outside the initial M11 implementation, and that native mobile credentials, background workers and ML access stay separate designs.
6. Phase 11A's architecture is approved and ADR 0005 is ACCEPTED. Implementation phases, real-data migration, route reopening, deployment and PR/merge each retain separate approval gates.
