## Implementation and contract

The new `202610220001_asset_ownership` version adds nullable UUID `public.asset.owner_id`, without a default or backfill. It adds `asset_owner_id_fkey` to `public.app_user(id)` (`MATCH SIMPLE`, validated and enforced, non-deferrable, `ON DELETE RESTRICT`, `ON UPDATE NO ACTION`), non-unique B-tree `asset_owner_created_id_idx` on `(owner_id, created_at DESC, id DESC)`, and enforced `asset_owner_required_check CHECK (owner_id IS NOT NULL) NOT VALID`. The check remains unvalidated on fresh and upgraded databases. Existing rows retain NULL owner and their original metadata/path values; new NULL writes and unrelated updates to NULL-owned legacy rows fail. Assigning a real user to an old row is deliberately outside this phase.

The runner checks PostgreSQL 18, `public`, Kysely metadata and the ordered known ledger before selecting a schema inspector. A pre-M11 history uses the unchanged historical M8 asset inspector and rejects premature owner fields/reserved names. A recorded M11 history uses a new exact ownership inspector. Auth schema inspection remains history-aware. Drift, missing history objects, partial ownership, wrong constraints/indexes/defaults, triggers, rules and RLS fail without repair. Advisory locking and Kysely transactional migration/ledger behavior remain. No migration runs at API startup; the production `AssetsModule` remains unmounted and the early asset lockdown remains active. The transitional Kysely owner type allows the retained unmounted asset service to compile; the database rejects ownerless writes, and 11C must make the application create input actor-derived and mandatory before any route reopening.

### Independent review corrections

The first review found that `pg_constraint` alone did not prove FK enforcement: a privileged operator could disable an internal FK trigger while its constraint remained valid. A disposable PostgreSQL 18 catalog probe established the four actual triggers. The M11 inspector now selects triggers by the exact `asset_owner_id_fkey` constraint OID and verifies exactly two `asset` triggers (`RI_FKey_check_ins`, AFTER ROW INSERT; `RI_FKey_check_upd`, AFTER ROW UPDATE) and two `app_user` triggers (`RI_FKey_noaction_upd`, AFTER ROW UPDATE; `RI_FKey_restrict_del`, AFTER ROW DELETE). It checks their `pg_class` relation/namespace, `pg_proc` function/`pg_catalog` namespace, internal flag, ordinary-session enable state `O`, non-deferrability, absence of a trigger condition/parent and exact `tgtype` event bits. Generated OID-bearing trigger names are never hardcoded. The separate M10 `auth_session_user_id_fkey` triggers remain valid and are not part of the ownership set. Tests disable one exact ownership trigger on each table and show that status, migration preflight and the startup readiness method reject the drift; after explicit re-enable, validation passes. Ledger and asset records remain unchanged throughout.

The second review found that the old single rollback test reached only the newest M11 `down()`. It was replaced by three explicit tests using M11-, M10- and M8-only providers as appropriate. Each asserts its own refusal message and compares the exact ledger, tables, columns, constraints, indexes, asset table identity and records before and after. Historical migration sources and inspectors were not changed.

Historical migration files `202610170001_initial_asset.ts` and `202610210001_authentication_foundation.ts`, and their M8/M10 inspectors, were not edited. Their source SHA-256 values matched HEAD: `0fed7889e36865660401745527479bb038849dd4531a8dfb41da1170233a1d89` and `af40c34f49abcd6cf3daa41f2cca427f14d1d54487689c4995bb013933e0b4f9` respectively.

## Data safety and limitations

No command targeted the development PostgreSQL connection, Docker volume or real storage. No existing photograph was opened or changed. Synthetic fixture paths were inert strings. This version does not map ownerless rows, authorize existing users to view them or reopen production media endpoints. PostgreSQL metadata bootstrap can leave valid empty metadata after an initial failure; partial metadata is rejected. The strict old M10 binary rejects an M11 schema, so mixed-version rollout is unsupported; a maintenance window and separate reviewed recovery plan are required. A real upgrade requires verified database/media backups, an isolated rehearsal and explicit separate approval. Restoring historical NULL-owned rows into an already-M11 schema may fail because `NOT VALID` still enforces the check on new writes; the data may need to be restored before installing the check. That sequence has not been rehearsed with real data. The migration takes PostgreSQL DDL locks, so operational timing remains untested on real data. Broad filesystem failure injection and crash reconciliation remain future work.
