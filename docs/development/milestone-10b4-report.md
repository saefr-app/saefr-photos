## Implemented contracts

- `POST /api/v1/auth/login`: exact `APP_ORIGIN`, JSON content type, `X-Saefr-Login: 1`, strict `{username,password}` body and no simultaneous cookie or bearer credential. Success returns the approved user/session/CSRF shape and an HttpOnly, SameSite=Lax cookie. Production uses `__Host-saefr_session` with Secure and Path=/; loopback development/test uses a distinct cookie name. Auth responses use `Cache-Control: no-store`.
- Each login generates 32 random credential bytes and stores only SHA-256 of those bytes. A separate random 32-byte CSRF token is bound to the row. PostgreSQL is consulted on every authenticated request for current user status and expiry; no authorization cache or bearer transport exists. Regular expiry is seven days; password-change-required expiry is 15 minutes; an eleventh live session gets a safe 409. Expired rows are unusable before pruning.
- `GET /api/v1/me`, `POST /api/v1/auth/password`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `GET /api/v1/auth/sessions`, and `DELETE /api/v1/auth/sessions/:id` follow the approved response shapes and status codes. Password change verifies the current password, updates the hash, clears the restriction and revokes all sessions transactionally; the user signs in again. Unknown and foreign session IDs both return 404. An invalid current cookie is cleared on the logout route when it can be identified safely.
- A global Nest guard defaults to denial except explicitly public health and login routes. Unsafe authenticated requests require exact Origin and the independent `X-CSRF-Token`. The typed actor carries user/session UUID, role and restriction status; the administrator role has no media bypass. The early Fastify asset boundary returns 401 without a valid session, fixed 503 for authenticated users and administrators, and safe 503 on session-database failure. HEAD has no body; no range or asset existence metadata is returned.
- A bounded, single-process limiter allows 30 login attempts per socket address and 10 per canonical username per 15 minutes, with equivalent counters for password reauthentication. Argon2 work is capped at two active operations with a 16-item queue; excess gets sanitized 429 with `Retry-After`. The production adapter limits JSON bodies to 8192 bytes. Proxy forwarding is not trusted by default.
- API startup validates the managed M8/M10 schema using the strict history-aware inspector before listening and never runs migrations. Swagger is disabled in the production composition. Existing media behavior remains covered in its isolated test module.

### Post-review logout-all correction

An independent review identified an in-flight login race. A deterministic PostgreSQL test paused login after successful password verification, committed logout-all, then resumed login. Before the fix, that login created a surviving session; the test failed as expected. Logout-all previously deleted sessions under the user-row lock but did not change any account state that the later login would recheck.

Logout-all now advances the existing `app_user.updated_at` value strictly inside its transaction before deleting sessions. Login reads that timestamp as a full-precision PostgreSQL revision before password verification and compares it again while holding the user-row lock before counting or inserting sessions. A login verified against a revision from before logout-all is rejected; a session inserted before logout-all acquires the row lock is deleted by logout-all. A genuinely new login that reads the revision after logout-all commits remains allowed. The test forces a future initial timestamp to verify the monotonic increment without depending on wall-clock timing. No migration, schema field or historical version changed. The row-lock order remains user first, then sessions, matching password change and operator recovery; existing recovery, expiry, session-cap and disabled-account tests still pass. In-flight requests already authorized before revocation remain the documented limitation.

Real-socket PostgreSQL tests now send malformed and oversized JSON to login at the Fastify parsing boundary. Both receive fixed JSON envelopes, `Cache-Control: no-store`, and no supplied private marker or framework error code. Malformed JSON receives 400 `Bad Request`; an oversized body receives 413 `Payload Too Large`. Neither creates a session.

## Security, data preservation and remaining risks

No development database migration, operator command against real data, photograph read/write/delete, storage mount, Docker volume operation, commit or push occurred. Test SQL was limited to random databases in the verified disposable container. The M8 and M10 migration versions and ledger in the existing installation remain untouched. Normal and handled-signal runner cleanup removed both final test containers; abrupt host termination can still strand a disposable container and requires identity-checked manual cleanup.

M10 cannot serve photos until M11 maps ownerless assets and enforces ownership/share predicates. Account administration and disable/last-admin HTTP rules are Phase 10B.5. Existing authorized requests cannot be withdrawn after a concurrent revocation commits. The in-memory limiter resets on restart and is unsuitable for multi-node deployment without a revised design. TLS/proxy/cookie behavior, a real backup/restore upgrade rehearsal and hardware-specific Argon2 capacity remain unverified. `/health/ready` checks database connectivity; startup performs the strict schema check, and later schema loss makes authenticated requests fail closed. Historical filesystem upload crash recovery and write/cleanup failure injection remain outstanding. This phase is not deployment approval.
