## E. Security invariants across phases

1. No public registration, bootstrap or password-reset endpoint.
2. No unauthenticated account administration or other sensitive endpoint; intended public health/readiness must reveal no user/media data.
3. No authenticated-user or administrator access to ownerless media before M11; no admin bypass, static media route or test-only production escape hatch.
4. No plaintext credentials, session tokens, password hashes, real secrets or private photo content in logs, response bodies, OpenAPI examples or committed files. Passwords may appear in validated request bodies and must be redacted from logs.
5. No automatic migration on API startup. Do not modify, baseline, reset or migrate the existing development database without a separate approved plan.
6. Do not alter historical migration source/ledger or existing asset rows. M10 migration tests use verified disposable PostgreSQL 18 only.
7. Do not access, overwrite, delete or bulk-clean the existing media directories or Docker volume.
8. Authentication failures and missing/incompatible schema fail closed with sanitized responses. A session cannot grant ownership that does not exist.
9. Every phase must preserve the security boundary in its own deployable composition. New code behind an unreviewed branch is not proof of deployment readiness.
10. No intermediate runnable application may activate functional login while the ownerless production asset endpoints remain unrestricted. Independent authentication-component tests are permitted before lockdown.

## F. Database and API contract checkpoint

The approved contract lives in [milestone-10-spec.md](milestone-10-spec.md#proposed-postgresql-schema). Phase 10B.2 implemented migration source for two public tables: `app_user` (UUID identity, 64-character canonical username, password hash, `admin`/`user`, `active`/`disabled`, password-change flag and timestamps) and `auth_session` (UUID identity, user FK with `ON DELETE RESTRICT`, unique 32-byte token hash, 32-byte CSRF token, expiry after creation and timestamps). All columns are NOT NULL with no defaults. Named primary/unique/check constraints and session user/expiry indexes are verified by PostgreSQL catalog inspection. No `asset` change or owner backfill. The historical first migration and legacy inspector remain unchanged; the new version is `202610210001_authentication_foundation`.

Fresh disposable installations apply M8 then M10. Managed M8 installations apply M10 only. Exact compatible legacy tables require explicit `--baseline-legacy` and retain their rows/table identity before M10 applies. Repeats are no-ops. The runner rejects reserved-name collisions before M10, and validates complete M10 tables only when its ledger version is present. The new version validates its result inside the migration transaction. No development installation was migrated.

Planned HTTP routes: `/api/v1/auth/login`, `/logout`, `/logout-all`, `/password`, `/sessions`, `/sessions/:id`; `/api/v1/me`; `/api/v1/users` create/list and `/api/v1/users/:id/disable`. No M10 API endpoint is currently implemented. No native bearer transport is proposed for M10. Asset HTTP operations are planned to fail closed until M11.

Phase 10B.3 added an internal `PasswordService` using Argon2id v19 with 64 MiB, three passes, one lane, independent 16-byte salts and 32-byte tags. It validates 15–128 Unicode code points and at most 512 UTF-8 bytes without normalization, rejects malformed Unicode and a small documented local common-password list, bounds stored PHC parameters before verification, and supports dummy-hash work for absent/invalid account hashes. `OperatorAccountsService` and `UsersRepository` create only fixed `admin`/`user` roles through distinct internal methods; bootstrap uses a transaction-scoped advisory lock and zero-user check, while recovery locks the selected row, replaces only its hash/required-change flag and revokes sessions in one transaction. Bounded expiry pruning uses PostgreSQL time. Standalone commands use only explicit `AUTH_ADMIN_POSTGRES_*` settings, exact `--confirm-database`, and hidden interactive password entry for bootstrap/recovery. No HTTP route or application module imports these operations.

## I. Known risks and blockers

Existing media upload crash-recovery and filesystem write/cleanup failure-injection gaps remain. None implies that the existing development database has been upgraded.

**Remaining gate:** Phase 10B.5 requires separate authorization. Applying migrations or running operator commands against the development database requires further, separate authorization and a reviewed backup/recovery plan. The M8 frozen asset inspector still requires an exact M8 asset table; future M11 ownership changes must evolve the current-state validator separately before deployment.
